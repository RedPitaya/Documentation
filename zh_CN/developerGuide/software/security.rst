#######################
安全注意事项
#######################

本页概述 Red Pitaya 在实际使用中的安全机制，以及用户在受控环境或暴露环境中部署系统时应考虑的事项。

Red Pitaya 主要面向开放式开发、硬件访问和快速原型设计。默认优先考虑易用性和开发灵活性。

.. note::

   本页提供实践指导，并非适用于所有部署场景的完整安全标准。如果设备用于生产、受监管或面向互联网的
   环境，请验证您自己的安全控制措施和操作流程。

基本原则
==================

* Red Pitaya 板卡是 Linux 计算机，可以根据您的策略进行加固。
* 默认行为偏向于开发访问，而不是锁定运行。
* 保持 OS 和板卡软件更新，以获取 Linux 及其生态系统的修复。
* 切勿在源代码中硬编码密码、API 密钥或令牌。
* 如果部署需要更严格的控制，请增加用户、服务和网络限制。

快速加固检查清单
=========================

1. 更改默认凭据，并使用强度高且唯一的密码。
2. 在可行的情况下，优先使用 SSH 密钥而不是密码认证。
3. 将 SSH 和 Web 访问限制在可信网络或 VPN 路径内。
4. 禁用或移除部署中不需要的服务。
5. 保持 OS 和软件栈更新，然后重新测试应用程序工作流。
6. 在应用重大安全策略变更前备份配置。

访问模型和 root 权限
================================

许多 Red Pitaya 应用程序通过内存映射接口控制 FPGA 寄存器。在默认 Red Pitaya 软件栈中，这通常意味着需要对底层系统资源进行提升的或特权的
访问。

**主要影响：**

* 配置采集、生成或其他 FPGA 连接功能的 Web 应用依赖特权硬件访问。
* 创建辅助用户并不总能为这些工作负载提供强隔离，因为应用程序路径仍然需要访问内存映射的 FPGA 控制接口。
* 如果未规划替代的权限路径就禁用默认 root 访问，可能会破坏预期功能。

因此，Red Pitaya 默认不强制实施严格的用户限制。需要更严格安全性的用户，应将板卡加固视为部署任务，并根据环境定制 Linux 权限、服务和网络暴露范围。

更严格环境中的一种可行架构：

* 仅以提升的权限运行最低限度的硬件控制组件。
* 在可行的情况下，让面向用户的服务作为非特权进程运行。
* 更改权限边界后，验证所有受影响的应用程序。

用户和认证
========================

* 为已部署的系统使用强密码，并定期轮换密码。
* 首先确定访问模型：是开发便利性，还是严格隔离。
* 如果禁用直接 root 登录，请验证所有必需的应用程序和服务仍能通过所选权限模型工作。
* 对于类似生产环境的设置，优先限制网络暴露范围（可信子网、VPN 或防火墙规则）。

.. note::

   不同 OS 版本、板卡型号和应用栈的安全行为可能有所不同。升级后请重新验证认证和权限方面的假设。

硬件访问和权限
===============================

为设备（GPIO、SPI、I2C、UIO、IIO、UART）授予访问权限时，应尽可能避免宽泛权限，只分配必需的权限。

建议的方法：

1. 为面向硬件的应用程序创建专用组。
2. 应用 udev 规则，将特定设备节点映射到这些组。
3. 如果访问路径支持非 root 运行，则让应用程序进程在该组下运行。

.. note::

   某些 FPGA 控制路径依赖特权内存映射访问。在这些情况下，仅使用组级设备权限可能不足以完全替代基于 root 的执行。

用于排查 udev 匹配的实用命令：

.. code-block:: shell-session

   udevadm info -a /dev/xdevcfg
   udevadm info -a /dev/uio0
   udevadm info -a /dev/spidev1.0
   udevadm info -a /dev/i2c-0
   udevadm info -a /dev/ttyPS1
   udevadm info -a /dev/iio:device0
   udevadm info -a /dev/iio:device1

部署说明
================

* 在安全架构中，将 Red Pitaya 视为通用 Linux 端点。
* 谨慎处理可写 FAT32 分区：FAT32 不具备 Linux 的所有权和权限属性。
* 启用自动启动前，验证启动脚本和服务文件。
* 将远程部署通道视为特权路径，并采取相应的安全措施。
* 如果必须面向互联网访问，请增加您自己的加固层（防火墙、网络分段、认证控制和服务最小化）。

自定义更改的责任
=================================

Red Pitaya 作为面向开发的平台提供官方 OS 和软件，并为受支持的版本提供更新。

Official repositories:

* :rp-github:`Main ecosystem repository <RedPitaya/tree/master>`
* :rp-github:`FPGA repository <RedPitaya-FPGA/tree/master>`

源代码的许可证和使用条款由相关仓库文件（例如 ``LICENSE`` 和 ``README``）定义，不同组件之间可能有所不同。

如果用户应用第三方修改或自定义更改（例如自定义内核、修改后的服务、外部软件包、自定义镜像或权限模型更改），则用户负责在自己的环境中验证这些修改的安全性、兼容性和运行行为。

Red Pitaya 无法保证第三方或用户修改的软件栈的功能或安全属性。
